# 03 · 追踪与状态

覆盖九步工作流的 **⑥ 落追踪**，也是「续写 / 接着写」时第一个要读的文件。

**核心判断**：长篇漂移不是记忆问题，是**选择**问题。小说比任何上下文窗口都长，塞得越多，单个事实分到的注意力越少。所以解法不是让模型记住全书，而是**每次只装进这一章需要的那一薄片**。

---

## 1. 单一权威：总表是唯一真源

```
追踪/总表.md   ★ 唯一真源（metadata_file，只有写手 + 追踪流程能改）
   ├── 上下文.md                 ← 派生（sidecar）
   ├── 逐章记录/第NNN章.md        ← 派生（sidecar）
   ├── 伏笔账本.md                ← 派生（sidecar）
   ├── 角色状态/{名}.md           ← 派生（sidecar）
   └── 时间线/作者真相.md、读者已知.md ← 派生（sidecar）
```

| 规则 | 说明 |
|---|---|
| **一写多读** | 状态变更只写总表；派生文件一律**从总表重渲染** |
| **手改派生 = 无效** | 重渲染时整份覆盖。**要改状态就去改总表** |
| **不反向解析** | Markdown 派生文件只给人/模型读，不解析回总表 |
| **未来计划不进追踪** | 「第几章揭示」写进卷纲/细纲，**不写成时间线既成事实** |
| **两个文件不能打架** | 角色在哪、知道什么只有一个答案——这才是不崩的根本 |

**识别办法**：拿到一个文件先问「真源还是派生」。凡能从总表推出来的，一律是派生。

---

## 2. 定长上下文卡（`追踪/上下文.md`）

**铁律三**：写第 300 章时喂给模型的上下文，和写第 30 章时**一样大**。

| 约束 | 值 |
|---|---|
| 顶层区块 | **固定 7 栏**，不多不少 |
| 体积 | ≤12288 字节（约 12KB） |
| 活跃角色 | 最多 **6** 人 |
| 活跃伏笔 | 最多 **8** 条 |
| 近章速记 | 只保留 **3** 章 |

> 这些是**下一章热上下文容量**，不是完整状态容量。完整状态在总表里。

### 七栏（顺序固定）

| # | 栏名 | 装什么 | 不装什么 |
|---|---|---|---|
| 1 | `## 当前位置` | 卷/单元、已写到第几章、故事内时间、当前场景 | — |
| 2 | `## 长期约束` | 最多 6 条**永久生效**的设定裁定；要加第 7 条先合并语义重叠项 | 过程决策、短期承诺 |
| 3 | `## 核心角色状态` | 在场核心角色快照（位置/目标/资源/关系/所知/未结线） | 一次性路人 |
| 4 | `## 活跃伏笔` | 已埋未回收的伏笔当前行 | 规划中的未来伏笔 |
| 5 | `## 近三章速记` | 最近 3 章各一句发生了什么 | 更早的历史 |
| 6 | `## 下一章承诺` | 下一章必须履行的承诺 | — |
| 7 | `## 连贯性风险` | 目前最容易写错的几处 | — |

**不塞进续写状态卡的东西**：文风指南、文件索引、普通待办、质检计数。塞进去就是拿容量换噪音。

## 3. 逐章记录（`追踪/逐章记录/第NNN章.md`）

| 约束 | 值 |
|---|---|
| 目标 | ≤1500 字 |
| 硬上限 | **3000 字**，超过必须压缩 |
| 内容 | **只记影响后续章节的变化**，不是剧情梗概 |

**写什么**：谁知道了什么、哪个伏笔回收了、时间往前走了多少、关系怎么变的、本章退役了什么约束。
**不写什么**：剧情复述、文风评价、情绪感想——那些留给正文自己。

栏目：`## 结果`（一句话局面）｜`## 人物变化`（谁的身份/状态变了）｜`## 伏笔变化`（表格：动作/ID/摘要/埋于/计划回收/状态）｜`## 时间线事件`（表格：动作/ID/故事内时间/客观事实/读者已知/揭示状态/揭示章）｜`## 新增约束`｜`## 下一章承诺`｜`## 本章退役登记`（不再生效的约束或风险，原样保留可查）

> 逐章记录只是**便于人阅读的紧凑变化记录**，不承诺单独无损重建全部当前状态；完整语义以总表为准。

## 4. 两条时间线：作者真相 ≠ 读者已知（铁律四）

| 文件 | 装的 | 用途 |
|---|---|---|
| `追踪/时间线/作者真相.md` | 作者知道的全部（**含未揭晓的真相**） | 写手自己知道凶手是谁 |
| `追踪/时间线/读者已知.md` | 读者目前为止看到的部分 | 决定角色能说什么 |

**唯一硬规则**：角色在对话里**只能说出「读者已知」范围内的信息**。
写第 40 章时，模型可以同时看见「凶手是谁」和「主角还不知道」——所以它不会让角色把答案说漏。

栏目：`## 已知`（读者实际看到的部分，不是客观全部）｜`## 误判`（读者/主角以为成立、实际不成立）｜`## 尚未揭示`（客观事实 + 计划揭示章号，`reveal_chapter` 必须为 `null`）

**纪律**：① `未揭示` 事件 `reveal_chapter` **必须为 `null`**；部分/完全揭示只能填**已经发生**的实际章节；② 计划揭示的章号写进卷纲/细纲，**不写进时间线**；③ 细纲「视角/信息差」一律取自 `读者已知.md`，**不另起一套**。

## 5. 脏标记（取自 mcp-writing 的 `metadata_stale` + checksum）

正文一改，依赖它的派生状态就**不再是事实**。脏标记让这件事显式化，而不是悄悄错下去。

| 环节 | 做法 |
|---|---|
| **记录基准** | 每章提交时，在总表记录该章 `body_sha256` |
| **置脏** | 正文（或细纲字数目标）改动 → 该章标 `dirty`，并向上标脏：上下文卡、逐章记录、伏笔账本、时间线 |
| **告警** | **脏着的派生文件不许进热上下文**——基于脏状态的推理不可靠，必须先收敛 |
| **收敛** | 重渲染派生文件 + 更新 `body_sha256` + 清脏 |
| **不自动改语义** | 只标记脏，**不自动重算**角色动机、伏笔含义这类编辑态内容——那归作者 |

### 总表里的校验区

```markdown
## 校验区
- state_revision：17
- 已提交至：第 17 章
- 脏标记：
  | 章 | body_sha256 | 状态 | 脏了什么 |
  |---|---|---|---|
  | 017 | a3f1… | 干净 | — |
  | 016 | 9c02… | **脏** | 正文改过 → 上下文卡/逐章记录/伏笔账本 |
```

**设计原则**：自动化**确定性、机械性**的东西（路径、字数、checksum、脏检测）；**不自动化**编辑性、解释性的东西（场景意义、因果、stakes、伏笔解读）——那归作者。

---

## 6. 重渲染流程

派生文件脏了就重渲染，**不要手改**。

```
① 读总表（唯一真源） → ② 按最新已提交章重算：上下文卡（7 栏）/ 逐章记录 / 伏笔账本 / 角色状态 / 两条时间线 → ③ 整份覆盖写回（不合并、不 diff） → ④ 更新校验区：body_sha256、清脏、state_revision +1 → ⑤ 跑一次检查（字数越界？过期伏笔？失活角色？）
```

**注意**：① 重渲染是**整份重建**，不是打补丁；② 派生文件被手改导致不一致时，**不要去改派生文件，也不要删总表重来**——重渲染一次即可；③ 有正文却缺追踪时，先按导入流程修复/迁移，**不猜进度**。

---

## 7. 每章收尾三件事（不隔夜）

| # | 动作 | 落到哪 |
|---|---|---|
| 1 | **更新总表** | 章节状态、字数、本章发生的事、角色状态变化、新埋/回收的伏笔 → `追踪/总表.md` |
| 2 | **重渲染派生文件** | 上下文卡、逐章记录、伏笔账本、两条时间线 |
| 3 | **跑一次检查** | 字数是否越界、是否有过期伏笔、是否有失活角色（>15 章未出场） |

```bash
python scripts/检查.py 项目根/    # 校验总表与派生文件一致、扫描过期伏笔
```

**顺序不能颠倒**：先写总表再重渲染；反过来会把「还没记进真源的变化」冲掉。
